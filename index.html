DEPLOYMENT · DIGITALOCEAN · OBSERVABILITY

signoz-digitalocean

Desired state for one SigNoz observability server: ClickHouse, ClickHouse Keeper, a Postgres metastore, the SigNoz application and the signoz-otel-collector ingester behind Caddy on a single guarded DigitalOcean Droplet in Amsterdam.

Same package, second provider: this is the signoz Package Skill that also runs signoz-vultr, selected onto DigitalOcean by provider-compute: digitalocean and the digitalocean-* keys alone, under the workspace Compute Provider Standard. signoz-digitalocean.bigconfig.online serves the dashboard and accepts OTLP/HTTP on /v1/logs, /v1/traces and /v1/metrics behind a bearer token generated on the server.

What is tracked here

colors.yml (the only editable desired state), the three installed signoz Package Skill payloads and their lockfile, root launchers copied from those payloads, toolchain files, documentation, and verification.md, the record of the live verification this deployment passed. Credentials live in gitignored .envrc.private; generated output in .colors/ is never committed.

Lifecycle

direnv allow
./green build
./green create --dry-run
./green create

Build and dry-run are credential-free and never read ~/.ssh. Real creation converges the droplet in the region's default VPC, its cloud firewall, the proxied Cloudflare record and the Compose stack, provisions the root account, and proves ingestion through the public path. Deletion stays guarded by compute-prevent-destroy: true, and a change of provider-compute on a profile with a machine in state is refused: a provider switch is a delete and a create, never an apply.

The machine keypair is not in this repository

This deployment runs in keygen mode: colors.yml carries no digitalocean-ssh-keys, so the package generates and owns ~/.ssh/signoz-digitalocean outside the checkout. Cloning this repository elsewhere does not carry machine access — copy the keypair deliberately, or create refuses rather than regenerating a key that cannot reach the live host.

Reaching the host

Convergence writes one ~/.ssh/config block following the workspace SSH Config Standard, so ssh signoz-digitalocean connects with no address, user or -i flag, and delete removes it before destroying the droplet.

Credentials

The root password is the one operator-supplied application secret and the account's only record. The OTLP ingestion bearer token and the Postgres password are generated on the server, mode 0600, and exist nowhere else; read the token from /etc/signoz/ingestion.env over SSH.
